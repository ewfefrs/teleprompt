# Наручный фото-ассистент для очков G2 — дизайн

**Дата:** 2026-09-11
**Статус:** согласовано с пользователем, готово к плану реализации
**Автор:** brainstorming-сессия

---

## 1. Что это и зачем

Персональный ассистент «объясни, что я вижу». Пользователь носит на запястье
маленькое устройство с камерой, выведенной под ладонь. По нажатию кнопки камера
снимает то, что в руке/перед ладонью, фото уходит на телефон, телефон отправляет
его в нейросеть с заготовленной инструкцией и выводит короткий ответ-объяснение
в умные очки Even Realities G2 — текстом, видит только пользователь.

**Назначение — легальное:** личный помощник для понимания предметов, ценников,
надписей, документов. **НЕ** для скрытого списывания или обмана третьих лиц.
Это зафиксировано как рамка проекта.

**Бюджет:** ≤ 1500 ₽ на железо (укладываемся впритык, ~1250–1400 ₽).

### Что уже готово (переиспользуем)
У пользователя есть рабочий проект Whisprompt / EvenHub-движок: связь телефон ↔ G2
по BLE и **вывод текста в очки уже работают**. Значит часть «ответ ИИ → очки» —
решена, её не переизобретаем.

## 2. Общая архитектура и поток данных

```
[Кнопка]
   │ нажатие
   ▼
[ESP32-CAM на запястье]  ── камера OV2640 по короткому FPC-шлейфу (~10 см) под ладонь
   │ снимает 1 кадр JPEG
   │ HTTP POST по WiFi
   ▼
[Телефон = точка доступа WiFi; ESP32 = клиент]
   │ приложение принимает фото на локальном HTTP-сервере
   │ шлёт фото + системную инструкцию в DeepSeek (по мобильному интернету)
   ▼
[DeepSeek  deepseek-v4-flash-vision-exp]
   │ короткий текстовый ответ
   ▼
[Приложение] ── вывод текста в очки G2 по BLE (готовый EvenHub-движок)
```

**Ключевые решения по потоку данных:**
- Фото передаётся **по WiFi, а не по BLE** (BLE на ESP32 слишком медленный для картинки).
- **Телефон раздаёт точку доступа, ESP32 подключается к ней как клиент.** Телефон при
  этом сохраняет мобильный интернет (hotspot шарит сотовую сеть), поэтому одновременно:
  принимает фото по локальной сети от ESP32 **и** ходит к DeepSeek по интернету
  **и** держит BLE к очкам. Android это умеет.
- ESP32 **инициирует** передачу (POST на телефон), т.к. только он знает момент нажатия.

## 3. Железо — наручный блок

### Форм-фактор
- Плата и питание — на **запястье** (как широкий браслет / под рукавом рубашки).
- Камера вынесена **коротким FPC-шлейфом ~10 см** под ладонь, объективом на то,
  что пользователь держит.
- **Почему запястье, а не предплечье:** камера OV2640 подключается параллельным
  интерфейсом (DVP) по плоскому шлейфу. Такой сигнал надёжен только на короткой
  длине (~до 10–15 см). Запястье → ладонь ≈ 8–12 см — в норме. Предплечье → ладонь
  (25–40 см) вышло бы за предел надёжности DVP (полосы, битые кадры). Поэтому длинный
  шлейф от предплечья **отвергнут** на этапе дизайна.

### Спецификация камеры
- OV2640 штатная (в комплекте ESP32-CAM), до 1600×1200 (UXGA).
- Съёмка с близкого расстояния (ладонь у объектива) → мелкий шрифт читается на уровне
  железа. **Отдельный объектив не нужен**, доплаты нет.
- Подсветки/вспышки **нет** (по решению пользователя).

### Смета (BOM)

| Компонент | Зачем | Цена, ₽ |
|---|---|---|
| ESP32-CAM (AI-Thinker, OV2640) | камера + WiFi + управление | ~500 |
| FPC-удлинитель шлейфа камеры ~10 см | вынести объектив под ладонь | ~150 |
| Аккумулятор LiPo 3.7 В ~500 мА·ч | питание | ~200 |
| Модуль зарядки TP4056 (USB-C) | зарядка от USB/повербанка | ~50 |
| Boost-преобразователь MT3608 (до 5 В) | стабильное питание при WiFi (без просадок/ребутов) | ~50 |
| Тактовая кнопка + выключатель питания + провода | спуск и вкл/выкл | ~150 |
| Корпус (печать/готовый) + ремешок/липучка | носить на запястье | ~150–300 |
| **Итого** | | **~1250–1400 ₽** |

Запас по бюджету почти нулевой. Если что-то дорожает — первым режем стоимость корпуса
(корпус пользователя не заботит, лишь бы было технически логично и удобно).

### Питание
- LiPo 3.7 В → **boost до 5 В** (MT3608) → на 5 В вход ESP32-CAM (у платы свой
  регулятор на 3.3 В). Boost нужен, чтобы WiFi-передача не роняла напряжение и не
  вызывала перезагрузки (известная болячка ESP32-CAM при питании «в притык»).
- Зарядка через TP4056 (USB-C).
- **Без deep sleep** (см. §4). Ресурс: ~500 мА·ч при постоянном WiFi ≈ **2–3 часа**
  работы от заряда. Заряжается «как телефон», по мере надобности. Пользователь принял.

## 4. Прошивка ESP32-CAM

**Режим: НЕ спать.** Устройство постоянно активно и держит WiFi-подключение к точке
доступа телефона. Плюс — мгновенный отклик (нет задержки на переподключение). Минус —
батарея ~2–3 часа; принято.

Логика:
1. Старт → подключиться к точке доступа телефона (SSID/пароль в конфиге прошивки).
2. Держать соединение живым.
3. **Нажата кнопка** (GPIO, например GPIO13) → снять один JPEG.
4. Отправить кадр `HTTP POST` на локальный адрес телефона
   (например `http://192.168.43.1:PORT/photo`, тело = JPEG).
5. Вернуться к ожиданию следующего нажатия.

Обработка ошибок на стороне ESP32:
- Нет точки доступа / нет соединения → индикация встроенным светодиодом платы
  (мигание), периодические попытки переподключения.
- POST не прошёл → одна повторная попытка, затем сигнал ошибки светодиодом.
- Антидребезг кнопки; игнор повторного нажатия, пока предыдущий кадр в работе.

## 5. Приложение на телефоне

Расширяем **существующий проект** (Whisprompt / EvenHub). Добавляем модули:

1. **Приёмник фото (локальный HTTP-сервер).** Поднимается на IP точки доступа телефона,
   слушает `POST /photo`, принимает JPEG.
2. **Клиент ИИ.** Отправляет фото + системную инструкцию в DeepSeek, получает текст.
   Интерфейс клиента абстрактный (один метод `explain(image, instruction) -> text`),
   чтобы при необходимости в будущем подменить провайдера — но **в v1 реализация одна:
   DeepSeek**.
3. **Вывод в очки.** Отдаёт полученный текст в G2 существующим механизмом показа текста
   (пагинация длинного текста — штатная возможность движка).

### Движок ИИ
- **DeepSeek, модель `deepseek-v4-flash-vision-exp`**, OpenAI-совместимый эндпоинт
  `/chat/completions`. Фото — base64 в блоке `image`. Ключ API в настройках.
- **Принятые риски (v1, осознанно):**
  - DeepSeek ужимает фото до ~800×800 → **мелкий шрифт на документах может теряться**.
    Для предметов/вывесок/крупных надписей — ок. Пользователь принял этот риск.
  - Эндпоинт экспериментальный (`-exp`) — может измениться/сломаться со стороны DeepSeek.
  - API платный (тариф V4-Flash), но на 1–2 фото/мин — доли рубля.
- Веб-интерфейс/автоматизация браузера **отвергнуты** — хрупко (капчи, разлогины,
  вёрстка), API даёт то же самое надёжно.

### Заготовленная инструкция
- Системный промпт-шаблон в настройках приложения. Пример:
  «Объясни простыми словами, что на фото. Коротко, 1–2 предложения, чтобы уместилось
  в очки».
- **v1 — один шаблон.** Несколько пресетов (объясни / прочитай / переведи) — потом.

### Обработка ошибок (приложение)
- Фото не пришло / таймаут ИИ → короткое «Ошибка, повтори» в очки.
- Ответ слишком длинный → пагинация штатным механизмом.
- Нет ключа/сети к DeepSeek → понятное сообщение в очки.

## 6. Границы v1 (YAGNI — сознательно НЕ делаем)

- Живой предпросмотр кадра в очки — нет (пользователь отказался; поток картинки в очки
  тяжёл для ESP32).
- Несколько пресетов инструкции — потом.
- Deep sleep / энергосбережение — потом (сейчас важнее мгновенный отклик).
- Переключатель на другого ИИ-провайдера (Gemini для мелкого текста) — интерфейс под это
  заложен, но реализация **не входит** в v1.
- Красивый корпус, вспышка/подсветка, индикация заряда — нет.

## 7. Модульная разбивка (единицы и их границы)

| Единица | Что делает | Интерфейс | Зависит от |
|---|---|---|---|
| Наручное железо | питание, кнопка, камера на запястье | физический (кнопка/USB-зарядка) | — |
| Прошивка ESP32-CAM | снять кадр по кнопке, отправить на телефон | `POST /photo` (JPEG) на телефон | точка доступа телефона |
| Приёмник фото (app) | принять JPEG по локальной сети | HTTP-сервер, отдаёт байты фото | WiFi-hotspot телефона |
| Клиент ИИ (app) | фото+инструкция → текст | `explain(image, instruction) -> text` | DeepSeek API, интернет |
| Вывод в очки (app, готов) | текст → G2 | существующий метод показа текста | BLE, EvenHub-движок |
| Конфиг/инструкция (app) | хранит промпт, ключ, SSID | настройки приложения | — |

Каждую единицу можно понять и протестировать отдельно.

## 8. Тестирование

- **Прошивка:** кнопка → JPEG → POST на mock-сервер на ПК; проверка целостности кадра,
  антидребезга, переподключения при пропаже WiFi.
- **Клиент ИИ:** прогон тестового фото через DeepSeek, проверка формата запроса/ответа,
  поведение при таймауте/ошибке ключа.
- **Приёмник фото:** отправить тестовый POST → убедиться, что байты дошли и переданы дальше.
- **E2E:** нажатие кнопки → текст в очках; замер задержки «нажал → текст».
- **Приёмочный тест мелкого текста:** снять документ, оценить читаемость ответа. Результат
  решает, понадобится ли позже Gemini-фолбэк.

## 9. Открытые/отложенные вопросы

- Точный свободный GPIO под кнопку на конкретной ревизии ESP32-CAM — уточнить при сборке.
- Порт локального HTTP-сервера и способ узнать IP hotspot на конкретной версии Android —
  уточнить в реализации.
- Реальное время работы от 500 мА·ч — замерить на прототипе; при неудобстве вернуться к
  варианту «батарея побольше» или light-sleep.
